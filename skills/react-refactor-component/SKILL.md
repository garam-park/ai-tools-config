# React 컴포넌트 리팩토링 (React Refactor Component)

한 파일에 뭉쳐 있는 React 컴포넌트를 **동작을 바꾸지 않고** 여러 모듈로 가른다. 목표는 파일 수를 늘리는 것이 아니라, 각 조각이 혼자 읽히고 혼자 테스트되게 만드는 것이다.

이 스킬의 핵심 주장은 두 가지다.

- **구조를 발명하지 않는다.** 대부분의 저장소에는 이미 잘 분해된 형제 모듈이 있다. 그 패턴을 찾아 따르는 것이 어떤 모범 구조보다 낫다.
- **이동과 수정을 섞지 않는다.** 옮기는 커밋에서는 아무것도 고치지 않고, 고치는 커밋에서는 아무것도 옮기지 않는다. 섞는 순간 회귀의 원인을 좁힐 수 없다.

## 트리거

**명시 호출**: `$react-refactor-component`, `/react-refactor-component`, "이 컴포넌트 쪼개줘", "구조 정리해줘"

**자동 발동** — 다음 두 조건을 모두 만족할 때만 발동한다.

- 대상이 React 컴포넌트 파일(`.tsx`/`.jsx`)이고, 한 파일 또는 한 컴포넌트 함수가 눈에 띄게 크다.
- 사용자가 "리팩토링", "쪼개기", "정리", "너무 크다", "읽기 어렵다" 같은 **구조 개선 의도**를 표현한다.

파일이 크다는 사실만으로는 발동하지 않는다. 버그 수정이나 기능 추가 중에 큰 파일을 만났다고 끌어오지 않는다. 그때는 요청받은 일만 하고, 분해가 필요해 보이면 한 줄로 언급만 한다.

**발동하지 않는 경우**

- 버그 수정, 기능 추가, 성능 최적화. (구조 변경이 아니다.)
- 리네임, 포맷팅, import 정렬, 타입 주석 추가. (일반 편집으로 처리한다.)
- React가 아닌 코드. (백엔드·CLI·라이브러리 모듈.)
- 이미 분해된 파일에 파일을 하나 더 만드는 작업.
- 설계 문서 검토. (`architecture-doc-review`를 쓴다.)

## 0단계 — 정찰 (건너뛰지 않는다)

코드를 옮기기 전에 세 가지를 확정한다. 이 단계를 건너뛴 분해는 저장소와 어긋난 구조를 만들고, 결국 다시 옮기게 된다.

### 0-1. 저장소의 기존 분해 패턴을 찾는다

같은 저장소에서 **이미 잘 나뉘어 있는 비슷한 화면**을 찾아 읽는다. 없으면 형제 디렉토리, 그것도 없으면 같은 프로젝트의 다른 앱.

```bash
# 디렉토리 구조가 가장 발달한 곳 찾기
find src -maxdepth 3 -type d | sort
# 파일 규모 분포 — 이미 잘게 나뉜 영역이 모범이다
find src -name '*.ts' -o -name '*.tsx' | xargs wc -l | sort -rn | head -30
# 테스트가 붙어 있는 모듈 = 경계가 제대로 잡힌 모듈
find src -name '*.test.ts*' | sort
```

확인할 것:

- 디렉토리 이름 (`hooks/`, `components/`, `stores/`, `constants/`, `utils/`)
- 파일 접미사 (`*.geometry.ts`, `*.storage.ts`, `*.domain.ts`, `*.helpers.ts`, `*.types.ts`)
- 컴포넌트 배치 (`components/<Name>/index.tsx`인가 `components/<Name>.tsx`인가)
- 훅 이름 규칙 (외부 SDK를 다루는 훅에 `use<대상><SDK>` 같은 선례가 있는가)
- 상태 공유 방식 (store가 있는가, 있다면 무엇인가)
- 파일 머리 주석 규칙 (`// What:` / `// Why:` 같은 관습이 있는가)
- 테스트 파일 위치 (모듈 옆인가 별도 디렉토리인가)

**찾은 패턴을 사용자에게 한 번 보고하고, 그것을 따르겠다고 명시한다.** 저장소에 패턴이 없을 때만 새 구조를 제안하며, 그때는 근거를 댄다.

### 0-2. 안전망을 진단한다

[references/safety-net.md](references/safety-net.md)의 1절 표를 채운다. 타입 검사·린트·테스트·빌드가 각각 무엇을 잡고 무엇을 놓치는지 확인한다.

특히 확인할 것:

- `tsconfig.json`의 `strict`
- `react-hooks/exhaustive-deps` 규칙이 켜져 있는가 (꺼져 있으면 의존성 오류를 사람이 봐야 한다)
- 대상 파일에 테스트가 있는가

### 0-3. 대상을 읽고 지도를 그린다

파일 전체를 읽는다. 훑지 않는다. 그리고 다음을 센다.

```bash
grep -n 'useState\|useRef' <파일>
grep -n 'useEffect(' <파일>
grep -n 'useCallback(\|useMemo(' <파일>
grep -n '^const \|^function \|^type \|^export ' <파일>
```

구간을 줄 번호로 나눈다: 모듈 상단(상수·타입·순수 함수) / 훅과 로직 / JSX / 진입점. **각 구간이 전체의 몇 퍼센트인지** 적는다. 이 비율이 어디부터 손댈지를 정한다.

## 1~6단계 — 분해 순서

순서가 곧 위험 관리다. **앞 단계는 되돌리기 쉽고 뒤 단계는 어렵다.** 뒤 단계를 먼저 하지 않는다.

각 단계는 **혼자서 커밋 가능**해야 한다. 단계가 끝난 시점에 앱이 동작하지 않으면 단계를 잘못 쪼갠 것이다.

| 단계 | 내용 | 동작 변경 | 되돌리기 |
| --- | --- | --- | --- |
| 1 | 상수·타입·순수 함수를 모듈로 (기준 C1~C4) | 없음 | 쉬움 |
| 2 | 추출한 순수 함수에 테스트 (기준 C5) | 없음 | 쉬움 |
| 3 | 파생 상태 제거, 이펙트 쪼개기, 의존성·cleanup 교정 (기준 A2·B1~B5·E2·E3) | **있음** | 보통 |
| 4 | 명령형 SDK 코드를 훅으로 (기준 E1·E4·E5) | 없음(의도상) | 보통 |
| 5 | 상태 군집을 훅으로 (기준 A1·A3·A4·A6·A7) | 없음(의도상) | 어려움 |
| 6 | JSX를 표현 컴포넌트로 (기준 D1~D6) | 없음 | 보통 |

판단 기준의 전문은 [references/extraction-criteria.md](references/extraction-criteria.md)에 있다.

**3단계는 다른 모든 단계와 성격이 다르다.** 유일하게 동작을 바꾸는 단계이고, 따라서 유일하게 테스트가 반드시 선행해야 하는 단계다. 3단계의 각 수정은 개별 커밋으로 남기고, 무엇이 어떻게 바뀌는지 사용자에게 먼저 알린다.

4·5·6단계는 "의도상 동작 변경 없음"이다. 실제로는 이펙트 실행 순서와 렌더 타이밍이 바뀔 수 있으므로, 매 단계 후 실제 앱에서 확인한다.

## 검증

매 단계 끝에 [references/safety-net.md](references/safety-net.md) 5절의 순서를 돌린다. 저장소의 실제 명령을 `package.json`에서 확인해 쓴다.

순수 이동 단계(1·2·6)에서는 diff가 정말 이동인지 함께 확인한다. 추가된 줄이 삭제된 줄보다 눈에 띄게 많으면, 옮기면서 뭔가를 고친 것이다.

## 보고 형태

### 착수 전

```markdown
## 정찰 결과

**따를 패턴**: {저장소에서 찾은 구조와 그 근거 파일}
**안전망**: {무엇이 잡히고 무엇이 안 잡히는지, 먼저 써야 할 테스트}
**대상 구성**: 상단 {n}줄 / 로직 {n}줄 / JSX {n}줄 / 진입점 {n}줄

## 분해 계획

| 단계 | 무엇을 | 어디로 | 위험 | 검증 |
| --- | --- | --- | --- | --- |

{동작이 바뀌는 항목은 따로 표시}
{이번에 손대지 않을 것과 이유}
```

계획을 보인 뒤 멈춘다. 승인 없이 1단계를 시작하지 않는다.

### 각 단계 후

무엇을 옮겼는지, 어떤 검증을 돌려 무엇이 나왔는지, 다음 단계가 무엇인지 짧게. diff 재생은 하지 않는다.

### 중간에 버그를 발견하면

리팩토링 중 기존 버그를 발견하는 일은 흔하다. **그 자리에서 고치지 않는다.** 발견 사실과 위치를 기록하고 계속 진행한 뒤, 리팩토링이 끝나고 별도로 다룬다. 지금 고치면 회귀가 생겼을 때 원인이 이동인지 수정인지 가릴 수 없다.

예외: 그 버그 때문에 분해 자체가 불가능한 경우(3단계 항목). 이때는 사용자에게 알리고 3단계 안에서 개별 커밋으로 처리한다.

## 하지 않는 것

- **동작 바꾸기** — 분해는 동작 보존이 전제다. 개선 아이디어는 기록하고 별도 작업으로 넘긴다.
- **구조 발명** — 저장소에 선례가 있으면 취향과 달라도 그것을 따른다.
- **파일 수 목표** — "10개 파일로 나눈다" 같은 목표를 세우지 않는다. 경계가 결정하게 둔다.
- **라이브러리 도입** — 상태 관리·폼·스타일 라이브러리를 이 작업에서 새로 들이지 않는다.
- **테스트 없이 위험 단계 진입** — 안전망이 부족하면 1·2단계까지만 하고 멈추고 그 사실을 말한다.
- **한 커밋에 이동과 수정 섞기** — 검증 불가능해진다.
- **전역 설정 변경** — 린트 규칙이나 타입 설정을 켜서 다른 파일에 경고를 쏟지 않는다. 확인용으로 잠시 켰다면 되돌린다.
- **다른 파일로 번지기** — 대상 파일과 그로부터 갈라져 나온 모듈만 건드린다.

## 다른 스킬과의 관계

- `align-intent` — 분해 범위가 크거나 사용자 의도가 갈릴 때 먼저 쓴다. 0단계 정찰 결과를 보고할 때 의도가 어긋나 보이면 정렬로 돌아간다.
- `semantic-commits` — 단계별 커밋을 나눌 때 쓴다. 이 스킬의 단계 구분이 곧 커밋 경계이므로 대개 필요 없지만, 한 단계 안에서 이동과 수정이 섞였을 때 갈라내는 데 유용하다.
- `architecture-doc-review` — 설계 *문서*를 평가한다. 이 스킬은 *코드*를 옮긴다. 둘을 바꿔 쓰지 않는다.
