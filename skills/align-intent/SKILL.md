# 의도 정렬 (Align Intent)

사용자의 설명을 받은 뒤 곧장 실행하지 않고, **이해한 바를 먼저 되돌려 말해 사용자 생각과 맞추는 게이트**입니다. 잘못 이해한 채로 작업해서 결과물을 통째로 버리는 상황을 막는 것이 목적입니다.

기본 루프:

1. 사용자가 설명한다.
2. 이해한 바를 자기 말로 되돌려 말하고, 어긋날 것 같은 지점을 짚는다.
3. 사용자가 확인하거나 고쳐 말한다.
4. 어긋났으면 2로 돌아간다.
5. 일치하면 합의 내용을 고정하고, 이대로 진행할지 한 번 더 묻는다.

## Platforms (Cross-Tool)

원본은 이 리포의 `skills/align-intent/`이며, `install-skills.sh`가 아래 도구 경로에 리포 작업 트리를 직접 가리키는 심볼릭 링크를 만든다. 어느 도구에서 호출되든 동작은 동일하다.

- **Claude Code**: `~/.claude/skills/align-intent/`
- **Codex / GitHub Copilot / OpenCode**: `~/.agents/skills/align-intent/`

`agents/codex.yaml`은 Codex가 사용하는 선택적 UI 메타데이터다. `$align-intent`는 Codex 전용 슬래시-달러 문법이라 다른 클라이언트에서는 동작하지 않는다. 다른 도구는 공통 동작을 정의한 `SKILL.md`만 사용한다.

## 트리거

**명시 호출**: `/align-intent`, `$align-intent`, "의도 확인", "내 말 이해했어?", "뭘 하려는지 알겠어?"

**자동 트리거** — 다음 중 하나에 해당하면 사용자가 부르지 않아도 실행 전에 정렬한다.

- 요구가 여러 문장·여러 요구사항으로 이루어져 있다.
- "그거", "저번 그 방식", "적당히"처럼 지시 대상이나 기준이 모호하다.
- 합리적인 해석이 둘 이상이고, 어느 쪽이냐에 따라 결과물이 달라진다.
- 되돌리기 어려운 작업 직전이다 — 파일·데이터 삭제, 마이그레이션, 대규모 리팩터, 외부 전송·게시, 이력 변경.
- 사용자가 앞선 결과에 "그게 아니라", "그런 뜻이 아니고"라고 반응했다. 이때는 바로 고치러 들어가지 말고 정렬부터 다시 한다.

**발동하지 않는 경우** — 정렬 자체가 부담이 되면 안 된다.

- 해석의 여지가 없는 단문 지시(파일 하나 읽기, 명령 하나 실행, 오타 수정).
- 이미 정렬된 의도 안에서의 후속 지시.
- 답만 하면 되는 질문. 답이 곧 검증이므로 사전 정렬이 필요 없다.
- 한 대화에서 같은 주제로 이미 정렬을 마쳤다. 같은 내용을 매 턴 다시 확인하지 않는다.

## 되돌려 말하는 방법

1. **자기 말로 바꿔 말한다.** 사용자의 문장을 그대로 복창하면 이해했는지 검증되지 않는다. 다른 단어, 다른 구조, 구체적인 대상으로 바꿔 말해야 오해가 드러난다.
2. **추상을 구체로 내린다.** "설정을 정리한다"가 아니라 "`skills/`의 SKILL.md 프론트매터를 X 형식으로 통일한다"처럼, 사용자가 "아니, 그건 아니고"라고 짚을 수 있는 수준까지 내린다.
3. **확신도를 솔직하게 표시한다.** 확실한 부분과 추측한 부분을 섞지 않는다. 추측은 추측으로 표시한다.
4. **틀렸을 가능성이 큰 지점을 먼저 내놓는다.** 맞을 것 같은 내용을 길게 나열하는 것보다, 갈릴 만한 지점 1~3개를 짚는 편이 훨씬 빨리 정렬된다.
5. **질문은 한 번에 하나.** 질문을 여러 개 쌓으면 사용자는 답하기 어렵고, 답이 뭉뚱그려진다.
6. **이미 명확히 말한 것은 되묻지 않는다.** 되묻는 순간 사용자는 자신이 한 말이 전달되지 않았다고 느낀다.

## 응답 형태

작업 크기에 따라 두 가지 형태를 쓴다. 사용자의 언어를 그대로 사용한다.

### Mode A — 짧은 재진술 (기본)

작은 요청, 되돌리기 쉬운 변경, 해석 갈래가 하나뿐일 때.

```markdown
제가 이해한 건: {2~4문장으로 자기 말로 바꾼 요약}.

{가장 갈릴 것 같은 지점 하나에 대한 질문}
```

### Mode B — 구조화 요약

다음 중 하나라도 해당하면 Mode B를 쓴다: 파일 3개 이상 변경 · 되돌리기 어려움 · 요구사항이 여럿 · 설계나 방향 선택이 포함됨 · 상당한 작업량.

```markdown
## 제가 이해한 의도

**목표**: {무엇을 달성하려는가}
**범위**: {건드릴 것}
**제외**: {건드리지 않을 것 — 확인받고 싶은 경계}
**가정**: {명시되지 않아 제가 채워 넣은 것}

**확실하지 않은 지점**
1. {갈릴 수 있는 해석}
2. {결정이 필요한 선택}

맞나요? 다르면 어느 항목인지 알려주세요.
```

`제외`와 `가정`은 빠뜨리지 않는다. 오해는 보통 사용자가 말하지 않은 부분을 채워 넣는 자리에서 생긴다.

## 어긋났을 때

1. 사용자가 고쳐주면 **틀린 부분만** 다시 제시한다. 맞았던 부분까지 통째로 다시 확인받지 않는다.
2. 두 번 반복해도 맞지 않으면 방식을 바꾼다. 설명을 반복하지 말고 구체적인 예시, 반례, 또는 선택지 두 개를 제시해 사용자가 고르게 한다.
3. 세 번을 넘기면 정렬 자체가 막힌 이유를 짚는다 — 같은 용어를 다른 뜻으로 쓰고 있는지, 배경 맥락이 빠져 있는지, 사용자도 아직 결정하지 못한 부분인지. 원인을 말로 꺼내면 대개 그 자리에서 풀린다.
4. 사용자가 "그냥 해봐"라고 하면 정렬을 중단하고, 남은 불확실 항목을 가정으로 명시한 뒤 진행한다.

## 정렬된 뒤

1. 합의된 이해를 한 문단으로 고정한다. 이후 작업은 이 문단을 기준으로 판단한다.
2. **진행 여부를 한 번 더 묻는다.** "이대로 진행할까요?" 명시적인 승인 없이 실행을 시작하지 않는다.
3. 사용자가 "정렬만 하고 멈춰"라고 했으면 합의 요약만 남기고 종료한다. 후속은 `lc-spec-task`, `ntn-spec-task`, `inp-spec-task` 같은 명세 스킬로 이어갈 수 있다.
4. 작업 중 합의와 다른 상황을 발견하면 혼자 판단해서 진로를 바꾸지 않는다. 그 지점만 짚어 다시 정렬한다.

## 가드레일

- 정렬 단계에서는 파일을 만들거나 고치지 않는다. 의도를 이해하는 데 필요한 최소한의 읽기·탐색만 한다.
- "제가 제대로 이해했나요?"만 묻고 끝내지 않는다. 이해한 내용을 먼저 내놓아야 사용자가 검증할 수 있다.
- 사용자를 시험하거나 가르치려 들지 않는다. 검증 대상은 사용자의 설명이 아니라 나의 이해다.
- 정렬을 이유로 작업을 미루지 않는다. 목표는 확인 절차를 늘리는 것이 아니라 재작업을 줄이는 것이다.

## 다른 스킬과의 관계

- `clarify`는 **사용자가 이해하지 못할 때** 설명을 잘게 쪼개는 스킬이다. `align-intent`는 반대 방향으로, **내가 사용자를 이해하지 못했을 때** 이해를 맞추는 스킬이다.
- `*-spec-task` 스킬은 정렬된 의도를 문서화된 명세로 옮기는 다음 단계다. 정렬은 대화 안에서, 명세는 문서로 남긴다.
