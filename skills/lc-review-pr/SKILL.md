# PR 검토 (Local Lifecycle)

기존 작업 PR을 리뷰부터 검증된 후속 조치까지 처리합니다. 사용자가 명시적으로 머지를 요청하지 않는 한 머지하지 않고 마무리합니다. 작업 문맥은 프로젝트의 `planning/` 문서에서 가져오며 외부 트래커는 관여하지 않습니다.

## PR 해석

1. 작업 ID, PR URL, PR 번호, 브랜치 이름, 현재 브랜치를 받습니다. 숫자 작업 ID는 `T<digits>`로 정규화합니다.
2. 저장소 README와 에이전트 안내 문서를 읽고 로컬 브랜치 상태를 확인합니다.
3. GitHub 통합이 있으면 PR 메타데이터, 코멘트, 리뷰, 체크에 그것을 우선합니다. 동등한 통합 커버리지가 없으면 비대화형 `gh` CLI를 사용합니다.
4. 작업 문맥이 필요하면 `planning/` 아래 작업 문서, 소속 마일스톤 문서, index 현황판을 읽습니다. planning 진입점이 없으면 PR·브랜치·커밋·diff만으로 요청한 리뷰 작업에 충분할 때만 계속합니다. 작업 문맥을 지어내지 않습니다.
5. PR, 브랜치, 저장소, 작업이 같은 작업을 가리키는지 확인합니다. PR이 없으면 사용자가 처음부터 끝까지의 흐름을 명시적으로 요청하지 않는 한 중단하고 `lc-create-pr`로 안내합니다.

## GitHub CLI 사용

`gh`는 설치·인증되어 대상 저장소에 연결되어 있다고 전제합니다. 환경을 확인하려는 목적만으로 `command -v gh`, `gh auth status`, `gh repo view` 같은 독립 점검을 유용한 작업 전에 실행하지 않습니다.

더 풍부한 GitHub 통합이 이미 있지 않는 한 PR 조회, diff, 체크, 코멘트, 메타데이터에 `gh`를 직접 사용합니다. `gh`가 없거나, 인증되지 않았거나, 저장소를 해석할 수 없어 필요한 `gh` 명령이 실패하면 현재의 정확한 실패를 설명하고 설정을 자세히 안내합니다.

- 설치: macOS는 `brew install gh`, 그 외 OS는 공식 GitHub CLI 패키지를 선택합니다.
- 인증: `gh auth login`을 실행하고 저장소와 맞는 GitHub 호스트를 선택한 뒤 HTTPS 또는 SSH를 고르고, 요청되면 repo 접근을 허용합니다.
- 확인: 대상 저장소에서 `gh auth status`와 `gh repo view`를 실행합니다.
- 저장소 문제: `gh repo view`가 실패하면 `git remote -v`를 확인하고 기대하는 `OWNER/REPO`를 설명한 뒤, 계속하기 전에 `origin`을 설정하거나 수정하도록 안내합니다.

실패한 `gh` 명령의 원인을 파악한 뒤에만 다른 GitHub 통합이나 사용자가 제공한 PR URL로 fallback합니다. PR을 조회할 경로가 없으면 추측하지 말고 아직 필요한 설정 단계와 함께 중단합니다.

## 리뷰 대상 확정

1. PR diff, 리뷰 스레드, 코멘트, required check, 최근 커밋, 로컬 작업 트리를 확인합니다.
2. 문서화된 merge criteria를 찾습니다. 없으면 준비 상태를 판단하기 전에 작업 문서와 diff에서 구체적 기준을 초안으로 작성합니다.
3. 관련 없는 로컬 변경은 건드리지 않습니다.
4. 광범위 리뷰 전에 해결되지 않은 코멘트, 실패한 체크 같은 구체적 외부 신호를 우선합니다.

## 리뷰와 진단

PR이 현재 필요로 하는 작업만 선택합니다.

- 리뷰 피드백: 미해결 스레드를 확인하고 실행 가능한 코멘트마다 영향을 받는 코드에 매핑합니다.
- CI 실패: 실패한 체크와 로그를 확인하고, 가능하면 로컬에서 재현하며, 새 실패와 관련 없는 기존 경고를 구분합니다.
- merge readiness: 구현과 검증을 모든 merge 기준과 비교합니다.
- 광범위 리뷰 요청: 동작, 회귀 리스크, 오류 처리, 테스트, 필수 문서를 점검합니다.

현재 도구가 집중 리뷰 코멘트나 CI 기능을 제공하면 그것을 사용합니다. 독립 워커나 서브에이전트를 쓸 수 있고 사용자가 다중 관점 리뷰를 요청했다면, 읽기 전용 리뷰 범위를 한정해 배정하고 심각도와 파일/라인 근거가 있는 발견을 요구합니다. 쓸 수 없으면 메인 세션의 집중 리뷰로 계속하고 그 한계를 밝힙니다.

## 필요한 수정 구현

1. 차단 요소 발견, 실행 가능한 미해결 코멘트, 실패한 required check를 먼저 처리합니다.
2. 변경은 PR 범위와 merge criteria 안에 유지합니다.
3. 워커가 분명히 분리된 구현 작업을 소유하지 않는 한 파일을 수정하게 하지 않습니다.
4. 명시적 승인 없이 stash, reset, rebase, 브랜치 삭제, force push, 사용자 작업 덮어쓰기를 하지 않습니다.

## 검증과 후속 조치 게시

1. 수정 후 저장소의 관련 빌드, 테스트, lint 체크를 실행합니다.
2. 저장소 커밋 메시지 컨벤션을 따라 관련 변경만 커밋합니다. 사용자가 명시적으로 요청하지 않으면 AI 귀속 트레일러를 추가하지 않습니다. PR 브랜치를 push합니다.
3. 동작이 실질적으로 바뀌었거나 리뷰어가 재확인을 요청한 경우에만 리뷰를 다시 실행합니다.
4. 검증된 수정이 반영된 뒤에만 리뷰 스레드에 답하거나 해결합니다.
5. 기준, 발견, 수정, 정확한 검증 명령, 잔여 리스크를 담은 간결한 PR 업데이트를 게시합니다.

## 마무리

사용자가 명시적으로 요청하지 않는 한 머지하지 않습니다. 여기서 planning 작업을 `done`으로 표시하지 않습니다. 머지 결정과 planning 확정은 사용자와 `lc-sync-milestone`의 역할입니다. 보고 내용:

- PR URL과 base/head 브랜치
- push된 후속 커밋
- 리뷰와 required check 상태
- 수행한 검증
- 미해결 발견과 잔여 리스크
- 사용자의 머지 결정에 넘길 준비가 되었는지 여부
