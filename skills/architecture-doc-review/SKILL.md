# 아키텍처 설계서 검토 (Architecture Doc Review)

설계서를 받아 14개 기준(표현·구조·책임·안전)으로 평가해 *잘된 설계서인지*를 판단한다. 평가의 근거는 항상 본문·표·도식의 인용으로 제시한다.

## Platforms (Cross-Tool)

원본은 이 리포의 `skills/architecture-doc-review/`이며, `install-skills.sh`가 아래 도구 경로에 리포 작업 트리를 직접 가리키는 심볼릭 링크를 만든다.

- **Claude Code**: `~/.claude/skills/architecture-doc-review/`
- **Codex / GitHub Copilot / OpenCode**: `~/.agents/skills/architecture-doc-review/`

## 트리거

**명시 호출**: `$architecture-doc-review`, "설계서 검토해줘", "이 설계 어때?"

**자동 발동** — 다음 중 하나에 해당하면 사용자가 부르지 않아도 발동한다.

- 사용자가 아키텍처·시스템·인프라 설계서를 붙이고 "어때?", "리뷰", "검토", "잘됐나?" 같은 평가 의도를 함께 표현한다.
- 인턴·주니어가 제출한 설계서를 PR 직전에 검토하는 상황.
- "다른 사람에게 그대로 넘겨도 부끄럽지 않은 수준인가?"를 자문하는 자리.

**발동하지 않는 경우** — 잘못된 발동은 오히려 방해가 된다.

- 일반 첨삭·문장 다듬기·번역·문법 교정. (기준 14개와 무관함.)
- 코드 리뷰. (PR diff 검토는 다른 도구.)
- UX 카피·제품 메시지 리뷰. (설계서가 아님.)
- 평가 의도 없이 문서를 단순 공유하는 경우.
- 한 문장·한 문단 수준의 짧은 채팅. (설계서가 아님.)
- 비-아키텍처 문서 (예: 회의록, 학습 노트, 일반 위키).

## 입력

둘 중 어느 것이든 받는다.

1. **파일 경로** — 설계서 파일(주로 `.md`)의 경로를 알려주면 읽어 평가한다.
2. **붙여넣은 마크다운** — 본문 전체를 대화창에 붙여 넣으면 그대로 평가한다.

이미지가 본문에 임베드되어 있어도 *텍스트로 환원 가능한 부분*까지만 평가한다. 도식의 시각적 평가는 범위 밖이다.

## 평가 절차

1. **문서 형태 확인** — 마크다운 본문인지, 다이어그램이 들어 있는지, 표가 있는지 빠르게 훑는다. 설계서가 아니면 발동을 거절한다.
2. **14개 기준 적용** — [references/rubric.md](references/rubric.md)의 기준을 순서대로 적용한다. 각 기준은 *통과 / 부분 / 미흡* 중 하나로 판정한다.
3. **프레임워크 보조 검증** — [references/frameworks.md](references/frameworks.md)의 7개 프레임워크로 *내용 누락*을 점검한다 (예: TOGAF 4계층 중 빠진 게 없는지, Well-Architected 6 기둥이 모두 다뤄졌는지).
4. **근거 수집** — 각 판정에는 본문·표·도식의 짧은 인용 또는 파일:줄 위치를 첨부한다. 추측만으로 단정하지 않는다.
5. **종합 판정** — 14개 중 어디가 가장 약한지, 어떤 묶음(표현/구조/책임·안전)이 깨졌는지 한 문장으로 정리한다.

## 결과 형태

다음 순서로 보고한다. 길이보다 **판정의 근거**를 우선한다.

### 1. 종합 판정 (한 줄)

> *예: "표현·구조는 안정적이나 책임·안전 묶음에서 소유·식별자 기준이 어긋나 재작업이 필요함."*

### 2. 14개 기준 점검표

| #   | 기준              | 판정              | 근거 위치             |
| --- | ----------------- | ----------------- | --------------------- |
| 1   | 메타-서술 금지    | 통과 / 부분 / 미흡 | 본문 L12, 표 3-2 등 |
| ... | ...               | ...               | ...                   |

(14개 모두 한 줄씩 채운다.)

### 3. 상위 이슈 3~5개

심각도순으로 나열한다. 각 이슈는 *어떤 기준이* 어긋났는지, *어디서* 어긋났는지를 적는다.

| 심각도 | 기준 | 위치   | 한 줄 설명 |
| ------ | ---- | ------ | ---------- |
| 상     | #11  | 표 3-2 | 수동/자동 경계 미명시 |

### 4. 자주 빠지는 5개 항목 체크

체크리스트 5개 ([references/rubric.md §6](references/rubric.md))를 한 번 더 훑는다.

- [ ] 도식이 한 명제인가?
- [ ] 미정 표시가 명시적인가?
- [ ] 자원의 소유 주체가 비어 있지 않은가?
- [ ] 책임 경계(음의 공간)가 적혀 있는가?
- [ ] 식별자와 별칭이 같은 줄에 섞여 있지 않은가?

### 5. (선택) 1~2줄 개선 제안

기본은 식별만 한다. 사용자가 *"어디를 어떻게 고치면 돼?"*라고 물으면 1~2줄로 어디를 어떻게 고치면 되는지 제안한다. 본문 전체를 새로 쓰지 않는다. 사용자가 직접 고친다.

## 하지 않는 것

- **문장 다듬기·교정** — 평가는 하지만 수정은 사용자가 직접 한다.
- **새 기준 추가** — 14개 외 기준(예: 팀 컨벤션, 회사 정책)은 적용하지 않는다. 별도 요청 시에만 다룬다.
- **의도 추측** — 작성자의 의도를 짐작으로 평가하지 않는다. *글에 적힌 것*만 평가한다.
- **도식 시각 평가** — 다이어그램이 *무엇을 보여주는지*는 평가하지만, *예쁘게 그려졌는지*는 평가하지 않는다.
- **점수 매기기** — 100점 만점 같은 종합 점수를 내지 않는다. *통과/부분/미흡*과 *상위 이슈*만 보고한다.
